# Mega UI UX 라이팅 계약

한국어 제품 UI와 접근 가능한 이름에 적용하는 필수 규칙입니다. 컴포넌트 기본 문구, 예제,
소비 앱의 제목·설명·버튼·입력·오류·알림 모두 같은 기준을 따릅니다.
코드 식별자, 개발자 문서, 원문 보존이 필요한 약관·인용, 사용자 입력에는 말투를 강제하지 않습니다.

## 근거와 적용 범위

토스가 2022년 11월 15일 공개한 [8가지 라이팅 원칙](https://toss.tech/article/21022)을 참고했습니다.
당시 공개된 원칙이며 토스의 현재 내부 규정 전체를 의미하지 않습니다.
아래 예시·컴포넌트 계약·검사 규칙은 Mega UI가 정한 기준입니다.

토스의 다섯 핵심 가치는 명확함, 간결함, 친근함, 존중, 공감입니다.
여덟 원칙은 이를 문장과 화면에서 실천하는 방향입니다.

| 원칙                   | 적용할 질문                                  |
| ---------------------- | -------------------------------------------- |
| Predictable hint       | 클릭 직후 할 일을 예상할 수 있나요?          |
| Weed cutting           | 빼도 뜻이 같은 단어가 있나요?                |
| Remove empty sentences | 제목을 되풀이하는 설명이 있나요?             |
| Focus on key message   | 지금 결정에 필요한 정보인가요?               |
| Easy to speak          | 소리 내 읽어도 자연스럽나요?                 |
| Suggest over force     | 거절할 선택을 존중하나요?                    |
| Universal words        | 은어나 배경지식 없이 이해할 수 있나요?       |
| Find hidden emotion    | 이 상황에서 사용자가 느낄 감정을 고려했나요? |

## 우리 문구 규칙

1. 설명·완료·오류는 해요체로 씁니다. 버튼과 메뉴는 `저장`, `파일 내려받기`처럼 행동형,
   필드·탭·상태는 `이메일`, `결제 내역`, `대기 중`처럼 짧은 명사형을 허용합니다.
   `입력해 주세요`처럼 작업에 필요한 요청은 허용합니다. 모든 문구에 `요`를 붙이지 않습니다.
2. 버튼에는 바로 실행되는 행동을 씁니다. 단독 `확인`, `확인하기`, `진행`, `클릭`, `여기`는 쓰지 않습니다.
   안내를 닫으면 `닫기` 또는 `확인했어요`, 상세로 이동하면 `결제 내역 보기`로 구분합니다.
   앞 단계가 분명한 다단계 폼의 `다음`은 허용합니다.
3. 한 문장에는 한 가지 메시지를 담고, 제목에서 설명한 내용은 본문에서 반복하지 않습니다.
   `성공적으로`, `정상적으로`, `정말 삭제` 같은 군더더기를 덜어냅니다.
4. 실패한 대상과 사용자가 할 수 있는 다음 행동을 알려줍니다. 모르는 원인을 추측하지 않습니다.
   `네트워크 오류`, `자동 복구`, `입력 보존`은 실제로 확인된 경우에만 말합니다.
   서버의 원시 예외·스택·내부 코드를 그대로 보여주지 않습니다.
5. 결제 금액·수수료·갱신 조건·삭제 범위·복구 가능 여부는 결정 전에 보이게 씁니다.
   간결함을 이유로 중요한 조건을 숨기거나, 구현에 없는 환불·보관 기간을 만들어 쓰지 않습니다.
6. 선택을 재촉하거나 거절을 비난하지 않습니다. `지금 안 하면 손해`, `혜택 포기하기` 대신
   사실을 설명하고 `나중에`, `계속 편집` 같은 중립적인 선택을 줍니다.
7. 같은 대상을 같은 이름으로 부릅니다. 한 흐름에서 `저장`과 `등록`, `삭제`와 `보관`을 섞지 않습니다.
   사용자에게 필요한 전문 용어는 유지하되 설명합니다. 개발 구현 용어로 제품 상태를 설명하지 않습니다.
8. 오류·삭제·결제에는 차분한 톤을 씁니다. 과장, 밈, 불필요한 감탄사·이모지를 넣지 않습니다.
   축하도 실제 완료가 확인된 뒤에만 보여줍니다.

## 컴포넌트별 계약과 예시

다음은 Mega UI용 예시이며 토스 문구를 인용한 것이 아닙니다. 행동·금액·조건은 실제 구현에 맞춥니다.

| 컴포넌트 / 상황                   | 피할 문구                            | 권장 문구와 조건                                               |
| --------------------------------- | ------------------------------------ | -------------------------------------------------------------- |
| `Button`, `MenuItem`, `BottomCTA` | 확인                                 | 변경 사항 저장 / 청구서 내려받기                               |
| `IconButton`                      | 휴지통 아이콘                        | 문서 삭제 — 모양 대신 행동을 `label`에 씀                      |
| `PageHeader`, `Heading`           | 설정을 관리할 수 있는 화면이에요     | 알림 설정 — 설명은 필요한 조건만 추가                          |
| `Field`, `Input`                  | 입력하세요                           | label: 이메일 / hint: 로그인할 때 사용할 주소예요              |
| `Field.error`, `FormErrorSummary` | 잘못된 입력이에요                    | 이메일 주소에 @를 넣어 주세요 — 실제 검증 조건과 일치          |
| `Dialog`, `ConfirmDialog`         | 정말 삭제하시겠습니까? / 확인 / 취소 | 문서를 삭제할까요? / 문서 삭제 / 계속 편집                     |
| 삭제 설명                         | 삭제를 진행해 주세요                 | 삭제한 문서는 복구할 수 없어요 — 실제 복구 불가일 때만         |
| `EmptyState`, `TableEmpty`        | 데이터 없음                          | 등록한 팀원이 없어요 / 팀원 초대하기 — 초대가 가능한 경우      |
| 검색 결과 없음                    | 오류가 발생했어요                    | 검색 결과가 없어요 / 검색 조건 지우기                          |
| `Alert`, 오류 `Result`            | 오류가 발생했어요                    | 팀 목록을 불러오지 못했어요 / 다시 불러오기 — 재시도 구현 필요 |
| `useToast`, 성공 `Result`         | 성공적으로 처리되었습니다            | 변경 사항을 저장했어요 — 저장 응답 성공 뒤 표시                |
| `ProgressBar`, 로딩 안내          | 잠시만 기다려 주세요                 | 파일을 올리고 있어요 — 진행률은 측정값만 표시                  |
| `NotificationList`                | 확인                                 | 읽음으로 표시 — 상세 열기와 읽음 상태 변경을 구분              |

범용 컴포넌트는 업무 맥락을 알 수 없으므로 기본 문구를 제공할 수 있습니다.
소비 앱은 `title`, `description`, `emptyMessage`, `error`, `label`, `children` 등 실제 API로
대상과 후속 행동을 구체화해야 합니다. 문구 때문에 존재하지 않는 prop을 만들지 않습니다.

## AI 필수 작업 순서

1. 이 문서와 `ai-guide.md`, 사용할 컴포넌트 API를 읽습니다.
2. 사용자의 목적, 클릭 직후 동작, 로딩·빈 결과·실패·성공 상태를 확인한 뒤 문구를 씁니다.
3. 위 표를 따라 UI와 접근 가능한 이름에 적용합니다. 문자열만 바꾸고 행동을 다르게 남기지 않습니다.
4. 아래 검사를 실행해 위반을 수정합니다. 검사 통과만으로 의미 검토를 생략하지 않습니다.
5. 완료 보고에 검사 결과와 의미 검토 결과를 남깁니다. 확인하지 못한 사실이나 미구현 행동은 명시합니다.

### 자동 검사

`npm run lint:ux`는 `src/`, `examples/`의 JS/TS/JSX/TSX/JSON 파일을 재귀 검사합니다.
CI의 `npm run check`와 `npm test`에서도 실행됩니다.

- `UX001`: `하십시오`, `하시겠습니까`, `바랍니다` 같은 관료적인 요청 표현
- `UX002`: `성공적으로`, `정상적으로`, `정말 삭제` 같은 정해진 군더더기
- `UX003`: `지금 안 하면`, `놓치면 손해`, `혜택 포기` 같은 정해진 압박 표현
- `UX004`: JSX 텍스트 또는 따옴표 문자열 전체가 단독 `확인`, `확인하기`, `진행`, `클릭`, `여기`인 경우

이 검사는 소스 텍스트 기반입니다. 주석·내부 문자열에도 일치할 수 있고, 조합된 문자열·외부 번역·
서버 응답의 의미는 판별하지 못합니다. `UX004`는 버튼 밖의 단독 문자열도 검토 대상으로 차단합니다.
오탐을 피하려고 문자열을 분할하거나 규칙을 끄지 않습니다. 원문 보존 등 정당한 예외가 있으면
검사 코드에서 경로·문구·사유를 한정하고 리뷰합니다. 디렉터리 전체 제외는 허용하지 않습니다.

### 의미 검토 — 자동화로 대신할 수 없음

- 버튼 이름과 실제 동작이 일치하나요? 닫기·취소·삭제·결제가 구분되나요?
- 실패·빈 결과·로딩·성공을 구분했고 다음 행동이 실제로 가능한가요?
- 금액·조건·복구 여부가 사실이며 중요한 정보가 빠지지 않았나요?
- 해요체와 용어가 일관되고 중복 설명·압박·불필요한 전문 용어가 없나요?
- 아이콘 이름·필드 오류·상태 알림도 읽기 쉽고 접근성 연결이 유지되나요?

## 다른 프로젝트에서 강제하기

패키지 설치만으로 소비 프로젝트의 AI 지침이나 CI가 변경되지는 않습니다.
소비 프로젝트의 루트 `AGENTS.md` 및 해당 AI 도구의 프로젝트 지침에 다음을 추가하세요.

```md
@mega-ui/react로 UI를 작성하기 전에
node_modules/@mega-ui/react/docs/ai-guide.md와
node_modules/@mega-ui/react/docs/ux-writing.md를 읽고 반드시 준수한다.
문구 검사와 UX 라이팅 의미 검토를 완료하기 전에는 작업을 완료로 보고하지 않는다.
```

소비 프로젝트에 다음 npm script를 추가하고 CI의 필수 검사에 연결합니다.
명시한 경로가 없거나 검사 대상 파일이 없으면 실패합니다. 번역 파일 경로도 함께 전달하세요.

```json
{
  "lint:ux": "node node_modules/@mega-ui/react/docs/check-ux-writing.mjs src"
}
```

AI 지침은 작업 의무를 정하고 자동 검사는 명시된 위반을 차단합니다.
모든 문맥적 원칙의 완전한 자동 강제를 보장하지 않습니다.
